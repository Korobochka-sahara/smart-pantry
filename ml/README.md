# ML — Smart Pantry

## 1. Назначение

Папка `ml/` содержит компоненты машинного обучения и обработки изображений для проекта Smart Pantry.

Основная задача текущего этапа — распознавание товарных чеков с помощью OCR (Optical Character Recognition).

Целевой сценарий:

1. Пользователь загружает фотографию чека через приложение.
2. Backend передаёт изображение OCR-сервису.
3. OCR-сервис распознаёт содержимое документа.
4. Парсер выделяет товарные позиции и извлекает необходимые характеристики.
5. Backend сопоставляет распознанные позиции с товарами в базе данных.
6. Пользователь проверяет результат и подтверждает добавление товаров в инвентарь.

В дальнейшем ML-компоненты могут использоваться для более точного распознавания товаров, обработки неоднозначных названий и других задач.

## 2. Архитектура

ML-часть отделена от основного backend, чтобы зависимости и модели машинного обучения не смешивались с зависимостями FastAPI-приложения.

Общая схема:

`Android → Backend (FastAPI) → OCR service → MinerU`

- **Android** — клиентское приложение, которое загружает фотографии и отображает результаты.
- **Backend** — отвечает за API, авторизацию, бизнес-логику, сопоставление с товарами и работу с базой данных.
- **OCR service** — отдельный HTTP-сервис для распознавания документов.
- **MinerU** — инструмент распознавания и структурирования содержимого документа.
- **Парсер** — преобразует результат OCR в структурированные товарные позиции.

Взаимодействие между backend и OCR-сервисом происходит по HTTP.

## 3. Структура папки

Основные компоненты, используемые или разрабатываемые на текущем этапе:

- `ocr_service/` — отдельный сервис распознавания чеков.
  - `main.py` — FastAPI-приложение OCR-сервиса и его HTTP endpoint.
  - `mineru_service.py` — обёртка над MinerU Python SDK.
  - `__init__.py` — обозначение пакета Python.
- `test_images/` — изображения для проверки качества распознавания.
- `ocr/` — эксперименты и тесты OCR-инструментов, в том числе EasyOCR и PaddleOCR, если соответствующие файлы сохранены в этой директории.
- `results/` — и подпапки в нём - .json файлы с результатами раболты разных моделей.
- `.venv/` — виртуальное окружение ML-части, если оно создано непосредственно внутри `ml/`.

Фактическое содержимое директорий может меняться по мере разработки.

## 4. Используемые технологии

### Python

Язык программирования для интеграции OCR, обработки результатов и разработки вспомогательных инструментов.

### MinerU

Основной OCR-инструмент на текущем этапе.

Используется для обработки изображения чека и получения структурированного результата, содержащего распознанный текст и табличные данные.

Результат может содержать HTML-таблицы, текст, изображения и другие элементы документа. Перед извлечением товарных позиций его необходимо обработать.

### EasyOCR

Использовался для сравнения качества распознавания текста на чеках.

### PaddleOCR

Использовался для сравнения результатов с другими OCR-инструментами.

### FastAPI

Используется для предоставления OCR-функциональности через HTTP API.

## 5. OCR service

OCR-сервис запускается отдельно от основного backend.

Пример запуска из директории `ml/ocr_service/`:

```powershell
python -m uvicorn main:app --host 127.0.0.1 --port 8001 --reload
```

В режиме разработки `--reload` позволяет автоматически перезапускать приложение при изменении исходного кода.

Основной endpoint:

`POST /ocr`

Endpoint принимает изображение в multipart/form-data и возвращает результат обработки.

Пример ответа:

```json
{
  "status": "completed",
  "tier": "standard",
  "markdown": "..."
}
```

- `status` — результат выполнения обработки.
- `tier` — режим обработки MinerU, переданный сервисом.
- `markdown` — распознанное содержимое документа.

Поле `markdown` может содержать HTML-разметку таблиц и встроенные изображения в Base64. Поэтому его не следует без предварительной обработки использовать как готовый список товаров.

## 6. MinerUService

`mineru_service.py` изолирует вызов MinerU от HTTP-логики.

Основные задачи сервиса:

- принять путь к файлу;
- проверить наличие файла;
- вызвать MinerU Python SDK;
- получить Markdown с результатом распознавания;
- обработать ошибки;
- выполнять синхронную OCR-операцию в отдельном потоке, чтобы не блокировать event loop FastAPI.

Сервис распознаёт документ, но сам по себе не определяет, какие позиции нужно добавить в инвентарь.

## 7. Следующий этап: парсинг товарных позиций

После OCR необходимо преобразовать результат распознавания в структурированные объекты.

Предполагаемые поля товарной позиции:

- `name` — распознанное название товара;
- `brand` — бренд, если его удалось определить;
- `quantity` — количество приобретённых упаковок или единиц товара;
- `package_quantity` — количество содержимого в одной упаковке;
- `package_unit` — единица измерения содержимого, например `g`, `ml` или `pcs`.

Цены не входят в текущую модель данных Smart Pantry.

Парсер должен:

1. Извлекать содержимое таблиц и очищать технические блоки.
2. Находить строки с товарными позициями.
3. Связывать название товара с относящимися к нему строками количества и единиц измерения.
4. Приводить количество и единицы измерения к согласованному формату.
5. Обрабатывать неполные и неоднозначные результаты.
6. Возвращать структурированные данные, которые можно проверить и сопоставить с товарами в базе данных.

Не все чеки имеют одинаковую структуру, поэтому парсер должен учитывать возможность ошибок OCR и неизвестных форматов.

## 8. Принципы разработки

- ML-зависимости не должны попадать в виртуальное окружение основного backend без необходимости.
- OCR и бизнес-логика должны оставаться разделёнными.
- Результат OCR не считается окончательно подтверждёнными данными.
- Неоднозначные товарные позиции должны проверяться пользователем.
- Тестирование следует проводить на нескольких чеках, а не только на одном изображении.
- Время обработки, ошибки и качество распознавания следует измерять отдельно.
- В репозиторий не следует добавлять виртуальные окружения, большие скачанные модели, временные файлы и кэш.
